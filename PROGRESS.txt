Project Centaur Progress
Last updated: 2026-05-31

Current state:
- Runtime mode checks now use a shared `ModeContext` object. `live_dry` defaults to the live environment, can read live broker state for readiness/risk review, and still cannot mutate live broker orders; explicit paper mode remains blocked from live broker sync/order-mutation paths.
- Entry orders, managed exits, and stale-order cancellations now pass through `ExecutionRouter` before broker submission/cancellation. This gives paper/live order actions one adapter choke point and makes `live_dry` record intended live actions without calling the live broker adapter. Live entry/exit/cancel actions also pass `LiveRiskGuard` re-checks for mode, activation, kill switch, broker, strategy where relevant, live account/sync readiness, entry capacity, latest-bar availability, live instrument/venue permission where derivable, same-paper-order validation where relevant, and entry notional.
- Live-dry now records intended entry/exit/cancel actions in tick state and persists router-intent audit rows in `execution_router_intents`; live-dry stale-order reaping and managed exits can report intended actions without mutating the live broker, and `--evidence-report` summarizes recent router intents.
- Centaur now has the first canonical instrument registry foundation. Vendor listings such as `ALPACA:BTC/USD`, `BINANCE:BTCUSDT`, and `COINBASE:BTC-USD` can map to `BTC-USD-SPOT` while preserving venue-specific signal/execution permissions.
- The instrument registry now returns a first-class `InstrumentRef` for resolved venue identity, and persistence paths use it when deriving canonical instrument metadata. Strategy logic still carries raw symbols plus metadata while the wider migration continues.
- Broker order rows and shadow proposal/outcome rows now persist `canonical_instrument_id`, `venue`, and `venue_symbol`, with supporting indexes, schema-bootstrap backfills for existing derivable rows, and status labels. Evidence rows can distinguish the canonical instrument from the venue listing that produced or executed it.
- Alpaca market-data adapter outputs now include canonical instrument metadata before the pipeline records latest bars, historical bars, or discovery candidates. This moves the canonical-instrument boundary earlier without changing prices, ranking logic, symbols, risk, or execution.
- New market-data latest-bar rows, historical backfill rows, and strategy-candidate signal rows now also persist `asset_class`, `canonical_instrument_id`, `venue`, and `venue_symbol`, with supporting indexes. Historical latest-bar/signal/backfill rows are not full-table backfilled inside normal schema bootstrap because that proved too heavy for the control-loop path.
- Discovery ranked candidates and strategy signals now preserve a serialized first-class `instrument_ref` from source market-data rows, keeping vendor symbol mapping visible through the strategy-evidence path without changing scores.
- The first market-data adapter boundary now exists under `centaur.market_data_adapters`; current Alpaca equity/crypto latest-bar fetches and historical equity/crypto backfill fetches go through `AlpacaMarketDataAdapter` while preserving the same symbols, sources, and runtime behavior.
- The first execution-adapter boundary now exists under `centaur.execution_adapters`; entry/exit order-request building plus `ExecutionRouter` submit/cancel now pass through this narrower order-planning and mutation interface, currently bridged to the existing broker adapters so live/paper order behavior is unchanged.
- The execution-adapter registry now resolves only `alpaca_paper` and `alpaca_live`. Scaffold-only IG and future vendors such as Binance/Coinbase fail at lookup until concrete adapters, tests, evidence surfaces, and explicit approval exist.
- `.venv-mac/bin/python main.py --adapter-inventory` now reports active, bridged, scaffold-only, and not-implemented adapter status so future provider work has an auditable activation surface before trading code changes.
- `.venv-mac/bin/python main.py --storage-separation-report` now provides a bounded read-only audit of the paper/live storage boundary. It samples recent broker-order, shadow-proposal, and strategy-fitness rows, reports missing runtime/source metadata, and states that the current implementation is PostgreSQL row-level provenance while physical paper/live database or schema separation remains pending.

- Optional `POSTGRES_SCHEMA` is now honored by the PostgreSQL operations store. When set, the schema is created/used for operations tables and shown in backend detail; when unset, current shared-schema behavior is unchanged. Actual paper/live deployment migration to separate schemas/databases remains a future checklist item.

The storage separation report prints lane schemas and directories so migration can be audited without duplicating the strategy brain.
